ADR-0004 · steps 1–2architecture

01A payment is recorded exactly once, even when the provider retries

Shipped in #201 webhook queue #202 handler shape only #203 idempotency key per event

Before, the payment provider's webhook was handled inside the web request that received it. When the provider didn't hear back fast enough it sent the same event again, and each copy created its own payment row, so a customer could appear to have paid twice. Now the web server only stores the event and answers right away. A queue worker records the payment, and a second copy of the same event is recognised and skipped.

Before 
flowchart TB
  P([Provider sends webhook]) --> H[Web request: record payment]
  H -->|slow reply| RT[Provider retries same event]
  RT --> H2["Web request: record payment again"]
  H2 -.-> D["Duplicate payment row"]
  style D stroke-dasharray: 4 3
After 
flowchart TB
  P([Provider sends webhook]) --> S["Store event, reply 200"]
  S --> Q[(job queue)]
  Q --> W[Worker: record payment]
  W -->|event id seen before| K[Skip]
  W -->|new event| R[(payments)]

Why it's better

  • Duplicates are impossible, not just unlikely. Replaying one webhook 5 times in staging produced 1 payment row, down from 5. A unique index on the provider's event id backs it up.
  • The provider stops retrying. The webhook now answers in ~40 ms instead of up to 9 s, well inside the provider's 5 s timeout, so there's nothing to retry in the first place.
  • A slow database no longer loses payments. If recording fails, the job retries from the stored event instead of depending on the provider to send it again.
Technical detail: two copies of one event
Two deliveries of the same event, after #203 
sequenceDiagram
  participant P as Provider
  participant API as /webhooks/payments
  participant W as Worker
  participant DB as Postgres
  P->>API: event evt_91 (attempt 1)
  API->>DB: INSERT webhook_events ON CONFLICT DO NOTHING
  API-->>P: 200
  P->>API: event evt_91 (attempt 2)
  API->>DB: INSERT … ON CONFLICT DO NOTHING (no row)
  API-->>P: 200

  Note over W,DB: one job per stored event, so one payment
  • webhook_events.provider_event_id is unique; the handler's insert is ON CONFLICT DO NOTHING, so a replay stores nothing and queues nothing.
  • The job carries only the event id. The worker re-reads the stored payload, so a retried job can't act on stale data.
  • Signature verification still happens in the web request, before anything is stored.
  • Not yet verified: the provider's live webhook in production (staging used the provider's replay tool).

02Overdue reminders actually go out

Shipped in #204 reminders on the queue #205 one reminder per invoice per day #207 closed, folded into #205 #213 overdue status on the invoice list

Customers with overdue invoices were supposed to get a reminder email every morning. They weren't getting anything: the server job that sent them had a typo that stopped it from ever running. Reminders now go out from the same queue as payments, at most once a day per invoice, and the invoice list shows which invoices are overdue with a button to send one now.

JobBefore (server crontab)After (queue)What changed
Overdue remindersdaily curl → /cron/remindersreminders.daily 09:00 localFired 212 times; a stray quote meant none reached the app.
Retry failed paymentshourly curlpayments.retry hourlySame logic, now visible in the job dashboard.

Why it's better

  • Reminders exist again. The first morning after the deploy, 38 reminders went out for invoices that had been overdue for up to 70 days.
  • No customer gets two in one day. A reminder records its date on the invoice; the daily job and the "Send reminder" button both check it.
  • A job that stops running is visible. Both schedules show their last run in the job dashboard instead of in a server crontab nobody looked at.
Technical detail
  • The crontab line was -H "x-cron-secret: "…": the extra quote made every run a shell syntax error, so cron logged the firing and nothing else.
  • invoices.last_reminded_on is set in the same transaction that queues the email, so a crash can't send without recording it.
  • #207 tried a per-customer limit instead; it was closed because one customer can owe several invoices that each deserve a reminder.

03An invoice's total comes from its line items, and only from them

Shipped in #206 derive totals from line items #208 repair migration #209 drop stored copies

The invoice total was stored in three places: on the invoice, on the PDF record and in the payment request. Editing a line item updated some of them, so a customer could open an invoice that said one amount and a PDF that said another. Now the total is calculated from the line items whenever it's shown, and the stored copies are gone.

Before: three stored totals 
flowchart LR
  L[(line_items)] -. "copied on save" .-> I[(invoices.total)]
  L -. "copied on render" .-> F[(pdfs.total)]
  L -. "copied on send" .-> P[(payment_requests.amount)]
After: one source 
flowchart LR
  L[(line_items)] -->|SUM at read time| V[invoice_totals view]
  V --> I[Invoice page]
  V --> F[PDF]
  V --> P[Payment request]

Why it's better

  • A PDF can't disagree with its invoice anymore. Before the fix, 41 of 3,200 invoices had a stored total that didn't match their line items.
  • The repair was reversible. The migration logged every old value it changed, and its down step restores them.

fixes

04–06Smaller fixes

04Export CSV no longer freezes the invoice list

#210 export from the cached result

The toolbar's Export CSV button re-ran the whole report on every click, which locked the page for up to 20 seconds on large accounts. Export moved into the ⋯ menu and now reuses the list that's already loaded.

05CI takes half as long

#211 cache dependencies in CI

Every CI run reinstalled all dependencies from scratch. Caching them cut a typical run from 7m 12s → 3m 40s.

06Invoice PDFs showed the wrong date near midnight

#212 PDF dates in the account's timezone

PDFs used the server's timezone, so an invoice issued late in the evening could carry the next day's date. They now use the account's timezone, like the rest of the app.
